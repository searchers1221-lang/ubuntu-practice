# Практическая работа №7. Межпроцессное взаимодействие (вариант A)

## Цель работы
Организовать обмен данными между процессами через pipe, именованный канал и сигналы.

## Запуск
    python3 pipe_demo.py
    python3 signal_demo.py &        # затем kill -INT $! два раза, fg и Ctrl+C
    python3 subprocess_pipe.py

## Результаты

### Неименованный канал (pipe_demo.py)
Ребёнок пишет строку в канал, родитель читает. Неиспользуемые концы закрыты: ребёнок закрывает конец чтения, родитель конец записи.
    Родитель получил: Привет от ребёнка!

Закрывать конец записи в родителе обязательно: иначе в канале остаётся открытый писатель и чтение никогда не получит EOF.

### Именованный канал (mkfifo /tmp/chan)
Тип файла в ls -l обозначен буквой p (pipe):
    prw-r--r-- 1 akmat akmat 0 Nov  2 21:34 /tmp/chan

Первая команда cat /tmp/chan запущена в фоне, пока никто не писал. Состояние задачи (jobs):
    [1]+  Running                    cat /tmp/chan > fifo_received.txt &

После echo hello > /tmp/chan cat получил данные и завершился. Принятое:
    hello

Почему cat "висит": открытие FIFO блокируется, пока с другой стороны канала никто не откроет его. cat открыл FIFO на чтение и ждёт писателя. Данные на диск не пишутся, они передаются напрямую через ядро. Как только echo открыл канал на запись, передача состоялась и cat завершился.

### Сигналы (signal_demo.py)
Процесс перехватывает SIGINT и печатает сообщение вместо завершения. Два сигнала отправлены командой kill -INT из того же терминала (программа была запущена в фоне), третий нажатием Ctrl+C после команды fg. Журнал:
    получен сигнал 2 (SIGINT), №1 из 3
    получен сигнал 2 (SIGINT), №2 из 3
    получен сигнал 2 (SIGINT), №3 из 3

Ctrl+C отправляет процессу переднего плана тот же сигнал SIGINT, что и kill -INT, поэтому поведение одинаковое.

### Конвейер ls | grep py через subprocess (subprocess_pipe.py)
    pipe_demo.py
    signal_demo.py
    subprocess_pipe.py
    

Вывод первой программы подключён ко входу второй через PIPE. Конец stdout у p1 в родителе закрыт, чтобы grep получил EOF после завершения ls.

## Ответы на контрольные вопросы
1. Разделяемая память самый быстрый механизм, потому что данные не копируются через ядро: оба процесса напрямую читают и пишут одну и ту же область памяти. Она же самая опасная, потому что ядро не синхронизирует доступ: без семафоров или мьютексов возникают гонки, которые проявляются нерегулярно.
2. Если все читающие концы закрыты, запись в pipe приводит к сигналу SIGPIPE, который по умолчанию завершает процесс. Если сигнал игнорируется, запись возвращает ошибку EPIPE (в Python BrokenPipeError).

## Выводы
Pipe подходит для связи родственных процессов, FIFO для неродственных через имя в файловой системе, сигналы для коротких уведомлений. Неиспользуемые концы каналов нужно закрывать, иначе процессы зависают в ожидании EOF.
