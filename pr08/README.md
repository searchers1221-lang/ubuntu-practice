# Практическая работа №8. Взаимоблокировки (вариант A)

## Цель работы
Воспроизвести взаимоблокировку, исправить её упорядочиванием блокировок и реализовать проверку безопасности состояния по алгоритму банкира.

## Запуск
    python3 deadlock.py             # программа с deadlock
    python3 deadlock_fixed.py       # исправленная версия
    python3 banker.py bank1.txt
    python3 banker.py bank2.txt
    python3 banker.py bank1.txt 1 1 0 2     # запрос P1 (1, 0, 2)

## Взаимоблокировка (deadlock.py)
Два потока захватывают lock_a и lock_b в разном порядке: T1 берёт A и ждёт B, T2 берёт B и ждёт A.

Как убедиться, что программа зависла: в начале файла стоит faulthandler.dump_traceback_later(3, exit=True). Если через 3 секунды программа не завершилась сама, faulthandler печатает, где стоит каждый поток, и завершает её. Без этой строки программа висела бы бесконечно, и остановить её можно только через Ctrl+C. Вывод:

    T2 взял B

      File "/usr/lib/python3.14/threading.py", line 1044 in _bootstrap
    
    Thread 0x00007ac121a9c6c0 [T1] (most recent call first):

В выводе видно, что "T1 взял A" и "T2 взял B" напечатаны, а "T1 взял B" и "T2 взял A" нет. По трассировке поток T1 стоит в функции thread1 на строке with lock_b, а T2 в функции thread2 на строке with lock_a: каждый ждёт замок, который держит другой. Основной поток стоит на join.

## Исправление (deadlock_fixed.py)
Оба потока всегда берут замки в одном порядке: сначала A, потом B.
    T1 взял A
    T1 взял B
    T2 взял A
    T2 взял B
    Готово: взаимоблокировки нет

Нарушено условие циклического ожидания (circular wait). Четыре условия взаимоблокировки: взаимное исключение, удержание и ожидание, отсутствие принудительного отнятия, циклическое ожидание. Одинаковый порядок захвата делает цикл невозможным.

## Алгоритм банкира (banker.py)
Need = Max - Allocation. Затем в цикле ищется процесс, у которого Need не больше Work; он считается завершившимся и возвращает свои ресурсы (Work увеличивается на Allocation этого процесса). Если завершились все процессы, состояние безопасно.

### bank1.txt (Available = 3 3 2)
    Need:
      P0: [7, 4, 3]
      P1: [1, 2, 2]
      P2: [6, 0, 0]
      P3: [0, 1, 1]
      P4: [4, 3, 1]
    SAFE, последовательность: P1, P3, P4, P0, P2

### bank2.txt (Available = 0 1 0)
    Need:
      P0: [7, 4, 3]
      P1: [1, 2, 2]
      P2: [6, 0, 0]
      P3: [0, 1, 1]
      P4: [4, 3, 1]
    UNSAFE

Безопасная последовательность не единственная. В методичке указана P1, P3, P4, P2, P0, а у меня получилась P1, P3, P4, P0, P2. Обе допустимы: после P1, P3, P4 свободно (7, 4, 5), и подходят и P0 (Need 7 4 3), и P2 (Need 6 0 0). Порядок зависит от того, как перебираются процессы. Главное, что состояние bank1 безопасно, а bank2 небезопасно.

### Запрос P1 (1, 0, 2) на bank1
    Need:
      P0: [7, 4, 3]
      P1: [1, 2, 2]
      P2: [6, 0, 0]
      P3: [0, 1, 1]
      P4: [4, 3, 1]
    SAFE, последовательность: P1, P3, P4, P0, P2
    Запрос P1 (1, 0, 2): ДА - выдать можно, безопасная последовательность: P1, P3, P4, P0, P2

Запрос не превышает Need (1, 2, 2) и Available (3, 3, 2), после пробной выдачи состояние остаётся безопасным, поэтому запрос удовлетворяется.

## Ответы на контрольные вопросы
1. Если все потоки берут ресурсы строго по возрастанию номера, то поток, держащий ресурс k, может ждать только ресурс с большим номером. Для цикла ожидания кому-то пришлось бы ждать ресурс с меньшим номером, а это запрещено порядком, поэтому цикл невозможен.
2. Алгоритму банкира нужно заранее знать максимальные потребности каждого процесса, а в универсальной ОС этого никто не знает. Кроме того, число процессов и ресурсов постоянно меняется, а проверка безопасности при каждом запросе дорога. Поэтому на практике используют предотвращение (порядок захвата) и обнаружение.

## Выводы
Взаимоблокировку вызывает циклическое ожидание замков. Её устраняет единый порядок захвата. Алгоритм банкира проверяет безопасность состояния и откатывает небезопасные запросы, но требует знания максимальных потребностей заранее.
