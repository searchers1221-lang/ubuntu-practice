# Практическая работа №4. Потоки (вариант A)

## Цель работы
Создавать потоки, наблюдать разделение адресного пространства и оценивать, когда многопоточность даёт выигрыш.

## Запуск
    python3 threads_demo.py
    python3 threads_race.py
    python3 threads_race2.py
    python3 download_demo.py

Число ядер (nproc): 8
Версия Python: Python 3.14.4

В обоих случаях итог верный. В версии Python, на которой я работал, инкремент counter += 1 глобальной переменной практически не прерывается переключением потоков, поэтому гонка в этом виде не проявилась. Язык этого не гарантирует: операция состоит из чтения, прибавления и записи и в принципе не атомарна.

### Загрузка 20 файлов (локальный сервер с задержкой 0,3 с на запрос)
Последовательно: 6.07 с
В 4 потока: 1.54 с

Потоки помогают, потому что задача ввода-вывода: поток почти всё время ждёт ответа сервера и в это время отпускает GIL, так что ожидания разных потоков накладываются друг на друга. Время упало примерно в 4 раза.

## Ответы на контрольные вопросы
1. У потоков одного процесса общие: адресное пространство (память, глобальные переменные), открытые файлы. У каждого своё: стек, регистры, счётчик команд, идентификатор потока.
2. В CPython есть GIL: байт-код в каждый момент выполняет только один поток, поэтому 4 потока не ускоряют вычисления. У отдельных процессов свои интерпретаторы и свои GIL, они работают параллельно на разных ядрах.

## Выводы
Потоки удобны для задач ввода-вывода и видны ядру как отдельные задачи. Для тяжёлых вычислений в CPython лучше процессы. Неатомарные операции над общими данными требуют синхронизации.
